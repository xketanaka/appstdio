# ファイル管理の仕様

## 全体の構成

| 区分 | 内容 |
|---|---|
| 組織共有ドライブ | テナント全体で使う |
| マイドライブ | 個人用 |
| 共有されたアイテム | 権限の付与によって見えているもの。実体は上の2つのどこかにある |
| ゴミ箱 | 削除されたもの |

ファイルの実体は Active Storage で保持する。

# グループ

グループの管理（作成・編集・利用停止など）の決まりは `doc/groups.md` を参照。ここには
ファイルの権限での扱いを書く。

* グループは**入れ子にできる**（部署の階層を表現する）
* 下位グループのメンバーは上位グループのメンバーでもある。`営業部 > 営業1課` のとき、
  営業部に共有すると営業1課のメンバーにも届く
* テナントごとに**「全員」グループ**を用意する。親を持たない。テナントの作成時に作る
* **「全員」のメンバーは行として持たない。** 定義上そのテナントの所属ユーザ全員なので、
  複製すると同期が必要になりずれる。権限解決で所属グループを求めるときに足す
* 「全員」も他のグループと同じ主体として扱う。共有先に指定でき、子フォルダで打ち消せる
* 利用停止中のグループ（とその下位）は、権限の解決では無いものとして扱う。共有設定は効かず、
  メンバーも上位グループのメンバーとして数えない。共有設定の行は残るので、再開すると元に戻る
* 所属の有効性（`tenant_users.status`）は権限解決では見ない。入口
  （`TenantContextFilter` とテナント選択）で判定済みのため

# ファイル・フォルダの操作権限

|  | ファイル | フォルダ |
|---|---|---|
| 閲覧者 | 参照・ダウンロード | フォルダ内のファイル・サブフォルダの参照 |
| 編集者 | ファイルの内容更新 | 配下のファイル・フォルダの作成、ファイル・フォルダのリネーム・移動(ただし移動先フォルダの編集権限も必要)、配下のファイル・フォルダの削除 |
| 管理者 | 共有設定の変更 | 共有設定の変更 |

* 権限(閲覧者、編集者、管理者)が付与される対象は個人、またはグループ
* 上記３つの権限の２つ以上を付与されている場合は、その強い方の権限として利用可能となる
* **上位の権限は下位を含む**（管理者は編集者・閲覧者の操作もできる）

# ファイル・フォルダの権限の継承

* ファイル・フォルダを新規作成したときは作成者が管理者権限をもつ、その他の権限は未設定
* 未設定の場合は、その親フォルダ(またはドライブルート)の権限を継承する
* **「未設定」は主体ごとに判定する。** 親フォルダに `営業部=編集者` があり、子フォルダに
  `総務部=閲覧者` だけを設定した場合、子フォルダでの営業部は編集者のまま継承される
* **UI 上は「親から継承した権限」として表示する**
* 親から継承した権限を子で打ち消すことはできる
* 打ち消しは付与された権限を取り消すもので、拒否という権限の付与ではない（与えたものをゼロにすることであってゼロよりマイナスにするものではない）
* 打ち消しは子孫にも効く。子で打ち消した権限を孫でさらに打ち消すことはできない（孫には打ち消す対象が無いため。別途付与することは可能）
* 同じノードで打ち消しと再付与を同時に行える。結果は再付与した段階になる
* **同じ主体への設定は、根に向かって最も近いものが効く。** 親に `営業部=編集者`、子に
  `営業部=閲覧者` があれば、子での営業部は閲覧者になる（子の設定で下げられる）。
  打ち消しもこの規則の一つで、最も近い設定が打ち消しならその主体は権限を持たない
* 主体が違う設定どうしは強い方を採る。本人への付与・所属グループとその上位グループ・「全員」の
  それぞれで上の規則を当てはめ、その中で最も強い権限が利用者の権限になる

## ドライブルートの権限

| ドライブ | 初期の権限 |
|---|---|
| 組織共有ドライブ | 「全員」グループが閲覧者 |
| マイドライブ | 本人が管理者 |

組織共有ドライブに専用の管理者は設けない。権限の変更はテナント管理者の特権アクセスで行う。

## 権限設定を超えるアクセス（特権モード）

* テナントの管理者・オーナー（`tenant_users.role` が `admin` / `owner`）は、ファイル画面で
  **特権モード**に切り替えたときだけ、すべてのファイル・フォルダに管理者権限でアクセスできる。
  組織共有ドライブの権限変更もこれで行う
* 特権モードでないときは、管理者・オーナーも一般の利用者と同じく、付与された権限で判定する。
  常に特権が効くと、共有された1ファイルからパンくずを辿るだけで他人のマイドライブ全体に
  入れてしまうため
* 特権モードはテナントごと・ログインごとに切り替える。テナントを切り替えたとき、
  ログアウトしたときは解除される
* 特権モード中であることは画面の上部に表示する。特権によって見えている個々の
  ファイル・フォルダには印を付けない
* 特権モードでの操作を、操作履歴で区別して記録しない
* 「共有されたアイテム」は特権モードに関わらず、付与された権限だけで判定する
* ファイル管理者グループ（個別に設定しなくても管理者権限を持つ人たち）を設ける。**実装は後回しでよい**

# 共有設定

* ファイル・フォルダの行のメニューと、フォルダの見出しの「共有」から開く。開けるのは、
  そのもの自身の管理者（特権モードを含む）
* 画面は上に「親フォルダから継承した権限」、下に「このフォルダ（ファイル）に設定された権限」を出す
  * 継承した行は、主体・権限・継承元のフォルダを出し、「打ち消す」「打ち消しをやめる」だけができる。
    上位のフォルダが見えない人には、継承元の名前を出さない
  * このもの自身の行は、権限を選び直すか外す。相手を探して加えると閲覧者で入る
* 加えられる相手は、有効・招待中の人と、有効なグループ（「全員」を含む）。利用停止中のグループは選べない
* 変えた内容は手元に溜め、「保存する」で開いたときからの差分だけをまとめて反映する。操作履歴に残す
* **管理者がいなくなる変更は保存できない。** 保存の前は管理者が実在する人まで届いていたのに、
  保存すると届かなくなる場合に断る。自分が管理者でなくなる変更は、他に管理者がいれば保存できる
  * 「届いている」は、有効・招待中の人、そういうメンバーのいる有効なグループ（下位を含む）、
    「全員」のどれかが管理者であること
  * もとから管理者の届いていないもの（組織共有ドライブのルートなど）は断らない
* あるファイル、フォルダに参照権限があり、かつその親フォルダの参照権限がない場合、「共有されたアイテム」となる

> **実装上の性質**
> 継承は上から下へ流れるため、継承によって見えているノードは親も必ず見えている。
> よって「親が見えないのに自分は見える」ノードは、明示的に権限が付与されたノードに
> 限られる。明示付与の件数は少ないので、全ノードを走査せずに求められる。

# 権限の判定

各ノードに根から親までの id の並び（`files_nodes.ancestor_ids`）を持たせ、判定のたびに
経路上の `files_permissions` から主体ごとに最も近い設定を選ぶ。

* 判定の結果（実効権限）は保存しない。一次情報は `files_permissions` だけにしておき、
  権限の変更・作成・グループ構成の変更で書き直しが起きないようにする
* `ancestor_ids` は DB のトリガが維持する。移動したときは配下もトリガが付け替える
* 検索は、候補の絞り込み（将来は Elasticsearch の全文検索）を先に行い、ヒットした
  node_id の権限だけを DB で判定する。判定の重さは「候補の件数 × 経路の深さ」になる
* 1テナントのノード数は 10 万未満を想定している。これを大きく超えて検索が間に合わなく
  なったら、主体ごとの実効権限を表に展開して持つ形を検討する

# 一覧の見え方

* **閲覧できるフォルダの中は、権限に関わらずすべての項目を一覧に表示する。** フォルダも
  ファイルも同じ扱いで、権限の無い項目は名前は見えるが、開けない・ダウンロードできない
  （Linux のディレクトリと同じ考え方）
* 名前が見えるかどうかは親フォルダの閲覧権限だけで決まり、その項目自身の権限は関係しない
* 一覧に並ぶ付帯情報（オーナー・更新日時・サイズ）は、閲覧できる項目にだけ表示する。
  権限の無い項目は名前だけにし、閲覧できないことが一覧から見てわかるようにする
* 名前を知られたくないものは、名前の付け方や置き場所（閲覧できる人を絞ったフォルダの中に
  置く）で守る。どういう規則で見えているのかがわかりやすいことを優先している

# 検索

* **検索は閲覧できるものだけを返す。** 名前での検索も内容の全文検索も同じ基準にする
* 一覧は「置き場所の中身を見る」機能、検索は「開けるものを探す」機能と目的を分けて考える。
  そのため、一覧に名前が出ている項目でも、閲覧できなければ検索では見つからない

# アップロード・ダウンロード

* アップロードできるのは、フォルダの編集権限を持つ人。作った人がそのファイルの管理者になる
  （フォルダと同じ）。1ファイルの大きさは 5GB まで（`Settings.files.max_upload_bytes`）
* 複数のファイルをまとめて上げられる。1ファイルずつ成功・失敗が決まる（移動と違い、
  まとめて取りやめにはしない）
* 同じフォルダに同じ名前のファイルがあれば、尋ねずにそのファイルの新しい版にする（「版」を参照）。
  同じ名前のフォルダがあるときはエラーにする
* 容量の上限を超えるファイルは断る
* ダウンロードできるのは、そのファイルを閲覧できる人。フォルダごとのダウンロードと、
  まとめてのダウンロード（zip）はまだ無い

# 版

* ファイルの内容更新は上書きせず版を残す
* 版には自動採番の番号（順序と参照のため）と、任意入力のラベル（「承認版」など）を持つ
* 保持日数を過ぎた古い版は実体を削除する。**最新版は日数に関わらず残す**
* 保持日数はテナントごとに設定する。既定は無制限
* 新しい版を足せるのは、**そのファイル自身の編集権限**を持つ人（名前の変更や移動が親フォルダの
  編集権限なのとは違う）。版の一覧と古い版のダウンロードは、閲覧できる人
* 新しい版の上げ方は2つ。行のメニューの「新しい版をアップロード」と、同じフォルダへ同じ名前の
  ファイルを上げること（尋ねずに新しい版にする）。上げたファイルの名前は使わず、元の名前のまま。
  アップロードの一覧には「『◯◯』の版3として保存しました」と出し、新しいファイルと取り違えないようにする
* 同じ名前のファイルを編集できない人が上げたときは、新しい版にせず断る
* 「この版を最新に戻す」は、古い版の中身で新しい番号の版を作る。古い版を消したり、番号を
  巻き戻したりはしない。中身は古い版と共有するが、使用量は版ごとに数える
* 一覧のサイズと更新日時、ダウンロード（ダブルクリック）は最新の版

# 同名の扱い

* 同一フォルダ内の名前の重複は許可しない。ただしゴミ箱の中のものは対象外
* 名前の比較では、大文字と小文字、全角と半角を区別する（`Report` と `report` は別の名前）
* 名前の前後の空白は取り除いて保存する。`/` と、`.` / `..` だけの名前は使えない
* 重複したときは自動で別名（「（1）」を付けるなど）にせず、エラーにして利用者に名前を直してもらう

# 移動

* **移動元の親フォルダと移動先のフォルダの、両方の編集権限**が要る。移すもの自身の権限は問わない
* 組織共有ドライブとマイドライブの間も移せる
* 複数をまとめて移すとき、1件でも移せなければ（移動先に同じ名前がある、それ自身やその中の
  フォルダへ移そうとした、など）**何も移さず**、理由をまとめて示す
* 今と同じ場所への移動は何もしない（操作履歴にも残さない）
* 移した直後は「元に戻す」で元のフォルダへ移し直せる。移し直しも1回の移動として扱い、
  同じ権限が要り、操作履歴にも残る。その間に元の場所へ同じ名前のものができていれば戻せない
* 「元に戻す」は今の場所を確かめずに元のフォルダへ移し直す（**あと勝ち**）。その間に別の人が
  さらに移していても、その移動を取り消す。ほかの操作と同じく、同時の変更は版（ロック）で
  守らず運用でカバーする判断にしている。困る場面が出てきたら、移動の API に「今ここにある
  はず」の場所を渡し、違っていれば何も動かさない形にする
* 移動したとき、そのノードに付いている権限設定は引き継ぐ。打ち消しも引き継ぐ
* 引き継いだ打ち消しに対応する親側の付与が無い場合、画面には表示しない

# 操作履歴

* 作成・更新・リネーム・移動・削除・復元・完全削除・共有設定の変更を記録する
* **参照とダウンロードは記録しない**

# 名前の変更

* 親フォルダの編集権限が要る。名前の決まりは「同名の扱い」と同じ
* ファイルの名前を変えるときは、拡張子まで含めた名前全体を変えられる。入力欄は拡張子を
  除いた部分を選んだ状態で開くので、打ち込めば拡張子は残る

# ゴミ箱

* 削除（ゴミ箱へ入れる）には、親フォルダの編集権限が要る。確認は出さず、直後の知らせの
  「元に戻す」で取り消せる
* フォルダを削除すると、配下もまとめてゴミ箱に入った扱いになる（配下だけを開くことはできない）。
  ゴミ箱に出るのは削除のときに選んだものだけで、元に戻すと配下も一緒に戻る
* 削除されたファイル・フォルダの**親フォルダの編集権限を持つ全員**のゴミ箱に表示される
* 復元できるのも同じ人たち。元の場所へ戻す。元のフォルダもゴミ箱にある、元の場所に同じ名前の
  ものができている、のどちらかなら戻さず理由を示す（まとめて戻すときは1件も戻さない）
* 削除した人・削除日時・サイズは、その項目を閲覧できるかに関わらず表示する。
  項目の付帯情報ではなく削除という操作の情報として扱い、復元するかの判断に使う
* 3ヶ月後に自動で完全削除する
* ここでいう「完全削除」はシステム上から見えなくなることを指す。**DB には論理削除済みの
  レコードとして残す**

# 容量制限

* テナント単位で上限を設ける。既定は 10GB
* **ゴミ箱の中身も、過去の版も使用量に含める**
* 上限に近づいたら警告を表示し、超過したらアップロードを拒否する（エラー表示）
* 完全削除のとき Active Storage の実体は削除する。レコードだけを論理削除として残す

## 仕様の帰結として注意する点

* **下位グループだけを除外することはできない。** 営業部に共有した場合、営業1課の
  メンバーにも必ず届く。打ち消しは「付与された権限を取り消す」操作であり、対象は
  付与された主体そのもの（この例では営業部）になる。営業1課を除外したい場合は、
  営業部への共有をやめて下位グループごとに共有する
* 組織共有ドライブの既定は閲覧者なので、**ファイルを追加するにはフォルダ単位で編集者を
  付与する**必要がある

# 機能の利用可否

* ファイル機能の利用有無はテナント単位で指定する（`files_settings.enabled`）。
  組織設定の画面で切り替える。利用しないテナントでは、メニューから「ファイル」を消し、
  `/files` 以下は 404 にする。保存されているファイルは消さない
* `files_settings` の行は `Tenant.setup!` で作る。新しいテナントは利用する状態で始まる
* ドライブは遅延作成する。組織共有ドライブはテナントで初めて開いたとき、
  マイドライブは各ユーザが初めて開いたとき

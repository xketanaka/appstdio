# ファイル管理の仕様

## 全体の構成

| 区分 | 内容 |
|---|---|
| 組織共有ドライブ | テナント全体で使う |
| マイドライブ | 個人用 |
| 共有されたアイテム | 権限の付与によって見えているもの。実体は上の2つのどこかにある |
| ゴミ箱 | 削除されたもの |

ファイルの実体は Active Storage で保持する。

# グループ

* グループは**入れ子にできる**（部署の階層を表現する）
* 下位グループのメンバーは上位グループのメンバーでもある。`営業部 > 営業1課` のとき、
  営業部に共有すると営業1課のメンバーにも届く
* テナントごとに**「全員」グループ**を用意する。親を持たない
* **「全員」のメンバーは行として持たない。** 定義上そのテナントの所属ユーザ全員なので、
  複製すると同期が必要になりずれる。権限解決で所属グループを求めるときに足す
* 「全員」も他のグループと同じ主体として扱う。共有先に指定でき、子フォルダで打ち消せる
* 所属の有効性（`tenant_users.status`）は権限解決では見ない。入口
  （`TenantContextFilter` とテナント選択）で判定済みのため

# ファイル・フォルダの操作権限

|  | ファイル | フォルダ |
|---|---|---|
| 閲覧者 | 参照・ダウンロード | フォルダ内のファイル・サブフォルダの参照 |
| 編集者 | ファイルの内容更新 | 配下のファイル・フォルダの作成、ファイル・フォルダのリネーム・移動(ただし移動先フォルダの編集権限も必要)、配下のファイル・フォルダの削除 |
| 管理者 | 共有設定の変更 | 共有設定の変更 |

* 権限(閲覧者、編集者、管理者)が付与される対象は個人、またはグループ
* 上記３つの権限の２つ以上を付与されている場合は、その強い方の権限として利用可能となる
* **上位の権限は下位を含む**（管理者は編集者・閲覧者の操作もできる）

# ファイル・フォルダの権限の継承

* ファイル・フォルダを新規作成したときは作成者が管理者権限をもつ、その他の権限は未設定
* 未設定の場合は、その親フォルダ(またはドライブルート)の権限を継承する
* **「未設定」は主体ごとに判定する。** 親フォルダに `営業部=編集者` があり、子フォルダに
  `総務部=閲覧者` だけを設定した場合、子フォルダでの営業部は編集者のまま継承される
* **UI 上は「親から継承した権限」として表示する**
* 親から継承した権限を子で打ち消すことはできる
* 打ち消しは付与された権限を取り消すもので、拒否という権限の付与ではない（与えたものをゼロにすることであってゼロよりマイナスにするものではない）
* 打ち消しは子孫にも効く。子で打ち消した権限を孫でさらに打ち消すことはできない（孫には打ち消す対象が無いため。別途付与することは可能）
* 同じノードで打ち消しと再付与を同時に行える。結果は再付与した段階になる
* **同じ主体への設定は、根に向かって最も近いものが効く。** 親に `営業部=編集者`、子に
  `営業部=閲覧者` があれば、子での営業部は閲覧者になる（子の設定で下げられる）。
  打ち消しもこの規則の一つで、最も近い設定が打ち消しならその主体は権限を持たない
* 主体が違う設定どうしは強い方を採る。本人への付与・所属グループとその上位グループ・「全員」の
  それぞれで上の規則を当てはめ、その中で最も強い権限が利用者の権限になる

## ドライブルートの権限

| ドライブ | 初期の権限 |
|---|---|
| 組織共有ドライブ | 「全員」グループが閲覧者 |
| マイドライブ | 本人が管理者 |

組織共有ドライブに専用の管理者は設けない。権限の変更はテナント管理者の特権アクセスで行う。

## 権限設定を超えるアクセス

* テナント管理者（`tenant_users.role` が `owner` / `admin`）はすべてのファイル・フォルダに
  アクセスできる。組織共有ドライブの権限変更もこれで行う
* ファイル管理者グループ（個別に設定しなくても管理者権限を持つ人たち）を設ける。**実装は後回しでよい**

# 共有設定

* あるファイル、フォルダに参照権限があり、かつその親フォルダの参照権限がない場合、「共有されたアイテム」となる

> **実装上の性質**
> 継承は上から下へ流れるため、継承によって見えているノードは親も必ず見えている。
> よって「親が見えないのに自分は見える」ノードは、明示的に権限が付与されたノードに
> 限られる。明示付与の件数は少ないので、全ノードを走査せずに求められる。

# 権限の判定

各ノードに根から親までの id の並び（`files_nodes.ancestor_ids`）を持たせ、判定のたびに
経路上の `files_permissions` から主体ごとに最も近い設定を選ぶ。

* 判定の結果（実効権限）は保存しない。一次情報は `files_permissions` だけにしておき、
  権限の変更・作成・グループ構成の変更で書き直しが起きないようにする
* `ancestor_ids` は DB のトリガが維持する。移動したときは配下もトリガが付け替える
* 検索は、候補の絞り込み（将来は Elasticsearch の全文検索）を先に行い、ヒットした
  node_id の権限だけを DB で判定する。判定の重さは「候補の件数 × 経路の深さ」になる
* 1テナントのノード数は 10 万未満を想定している。これを大きく超えて検索が間に合わなく
  なったら、主体ごとの実効権限を表に展開して持つ形を検討する

# 一覧の見え方

* 権限の無いフォルダも一覧に表示する（名前は見えるが開けない）

# 版

* ファイルの内容更新は上書きせず版を残す
* 版には自動採番の番号（順序と参照のため）と、任意入力のラベル（「承認版」など）を持つ
* 保持日数を過ぎた古い版は実体を削除する。**最新版は日数に関わらず残す**
* 保持日数はテナントごとに設定する。既定は無制限

# 同名の扱い

* 同一フォルダ内の名前の重複は許可しない。ただしゴミ箱の中のものは対象外

# 移動

* 移動したとき、そのノードに付いている権限設定は引き継ぐ。打ち消しも引き継ぐ
* 引き継いだ打ち消しに対応する親側の付与が無い場合、画面には表示しない

# 操作履歴

* 作成・更新・リネーム・移動・削除・復元・完全削除・共有設定の変更を記録する
* **参照とダウンロードは記録しない**

# ゴミ箱

* 削除されたファイル・フォルダの**親フォルダの編集権限を持つ全員**のゴミ箱に表示される
* 復元できるのも同じ人たち
* 3ヶ月後に自動で完全削除する
* ここでいう「完全削除」はシステム上から見えなくなることを指す。**DB には論理削除済みの
  レコードとして残す**

# 容量制限

* テナント単位で上限を設ける。既定は 10GB
* **ゴミ箱の中身も、過去の版も使用量に含める**
* 上限に近づいたら警告を表示し、超過したらアップロードを拒否する（エラー表示）
* 完全削除のとき Active Storage の実体は削除する。レコードだけを論理削除として残す

# 未決定の項目

実装に入る前、または実装しながら決める。

（現時点で未決定の項目はない）

## 仕様の帰結として注意する点

* **下位グループだけを除外することはできない。** 営業部に共有した場合、営業1課の
  メンバーにも必ず届く。打ち消しは「付与された権限を取り消す」操作であり、対象は
  付与された主体そのもの（この例では営業部）になる。営業1課を除外したい場合は、
  営業部への共有をやめて下位グループごとに共有する
* 組織共有ドライブの既定は閲覧者なので、**ファイルを追加するにはフォルダ単位で編集者を
  付与する**必要がある

# 機能の利用可否

* ファイル機能の利用有無はテナント単位で指定する
* ドライブは遅延作成する。組織共有ドライブはテナントで初めて開いたとき、
  マイドライブは各ユーザが初めて開いたとき
